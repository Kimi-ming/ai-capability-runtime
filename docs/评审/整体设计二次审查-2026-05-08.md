# 整体设计二次审查：从概念完整到工程闭环

日期：2026-05-08

本文是对 `docs/设计/整体系统设计-v1.md` 的二次架构审查。目标不是推翻上一版，而是把“看起来完整”的系统模型继续压实到工程对象、验收门槛和后续任务。

## 结论

当前方向成立：OpenCap 应继续坚持 `Capability-first`、`Runtime Kernel`、`Evidence Registry` 和协议中立 adapter。真正需要补强的是工程可执行性：哪些对象是公共契约，哪些账本必须存在，哪些证据能证明安全边界没有被绕过。

一句话：

```text
下一阶段不是继续扩概念，而是把五个平面压成类型、账本、卡片、Gate、Profile 和测试。
```

## 外部标准再校准

本轮对齐的外部信号：

- [MCP 规范 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic)：MCP 已经把协议分成 base protocol、lifecycle、authorization、server/client features 和 utilities。OpenCap 的 MCP 层应保持 adapter 地位，不能把 MCP 的 Host 行为写进 Runtime Kernel。
- [A2A 最新规范](https://a2a-protocol.org/latest/specification/)：A2A 强调 Agent Card、任务生命周期、认证授权、多传输和任务状态。OpenCap 未来需要 A2A profile，但 Capability 本身不能伪装成 Agent。
- [OpenAI Apps SDK](https://developers.openai.com/apps-sdk)：Apps SDK 以 MCP server 和 ChatGPT app 分发为核心。OpenCap 可以服务于 ChatGPT App，但不能把 Apps SDK 当成唯一生态入口。
- [SLSA 规范](https://slsa.dev/spec/) 与 [Sigstore 文档](https://docs.sigstore.dev/)：能力包、发布物和未来 Registry index 需要 provenance、签名和可验证来源。V1 不必实现签名，但数据模型必须预留 provenance 字段。

## Gate 统一模型

目前设计里有很多门禁：data egress、policy、quota、budget、revocation、outbound、audit preflight、metadata lint。它们应该共享统一结果结构。

```ts
interface RuntimeGate<I, E> {
  id: string;
  stage: "pre_secret" | "pre_execution" | "post_execution";
  evaluate(input: I): Promise<GateDecision<E>>;
}

interface GateDecision<E> {
  gate_id: string;
  decision: "allow" | "ask" | "deny" | "block";
  reason_code: string;
  summary: string;
  evidence: E;
  hard_boundary: boolean;
}
```

关键约束：

- `hard_boundary: true` 的 gate 不能被 override/breakglass 绕过。
- 所有 gate decision 都必须进入 redacted audit evidence。
- `ask` 只能由 confirmation/consent 处理，不能由 executor 处理。
- Secret Resolver 只允许在所有 `pre_secret` gate 通过后运行。

## 账本分层需要工程化

四种账本不是四份文档，而是四类可查询数据。

| 账本 | V1 最小存储 | 未来扩展 | 关键查询 |
| --- | --- | --- | --- |
| Capability Ledger | installed manifest + metadata JSON | signed registry index | 某能力从哪里来、是否 revoked |
| Policy Ledger | local policy revision file + audit rows | signed policy bundle | 某次调用用了哪版策略 |
| Invocation Ledger | SQLite audit log | OTel/export API | 某次调用发生了什么 |
| Compatibility Ledger | YAML/JSON evidence record | conformance service | 某 Host/profile 是否通过 |

实现时不要先做复杂数据库，但类型和查询语义要先定。

## 卡片是生态 UX 的核心

OpenCap 未来能否被人理解，不只靠日志，而靠卡片。

| 卡片 | 最小生成时机 | 必须包含 | 禁止包含 |
| --- | --- | --- | --- |
| Capability Card | `opencap list --json` 或 registry page | id、version、summary、risk、permissions、auth、lifecycle | secret 原文、未经 lint 的模型指令 |
| Trust Card | registry review 或 install 后 | tests、review、maintainer、advisory、quality、provenance | “绝对安全”承诺 |
| Consent Card | 每次 ask 前 | action、target、egress data classes、risk、policy reason | 模型自由生成的授权文案 |
| Compatibility Card | Host test 后 | host、version、profile、checks、known gaps | 泛泛的“兼容所有 Host” |

这四张卡片应成为 Console、CLI、Registry Web 和 future Cloud 的共同 UI 语言。

## Profile 不只是兼容声明

Profile 应包含三层：

1. `profile spec`：要求是什么。
2. `evidence record`：何时、在哪个版本、对哪个 Host 跑过。
3. `failure semantics`：失败时用户会看到什么、Runtime 会不会执行。

没有 evidence record 的 profile 只能叫 Draft 或 Experimental，不能叫 Compatible。

## Registry 需要区分三种状态

Registry 设计后续要明确三种状态：

| 状态 | 含义 | 关键字段 |
| --- | --- | --- |
| Source Registry | Git 中的能力包来源 | path、commit、maintainer、review |
| Local Cache | 本地可安装索引 | registry revision、package digest、advisory snapshot |
| Installed State | Runtime 实际使用副本 | install time、manifest digest、policy snapshot、lifecycle snapshot |

这样才能处理“Registry 更新了 advisory，但用户本地仍安装旧版本”的情况。

## 供应链信任要预留但不抢跑

V1 不需要马上实现 SLSA/Sigstore，但应该避免以后补不进去。

建议现在就预留：

- `manifest_digest`
- `package_digest`
- `registry_commit`
- `review_record_digest`
- `provenance_uri`
- `signature_uri`
- `builder_id`
- `source_uri`

这些字段可以先为空，但对象模型要允许存在。
