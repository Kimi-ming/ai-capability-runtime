# 整体系统设计 V1

本文把 OpenCap 从“很多设计文档”收敛成一个可执行的系统模型。它不是新的功能清单，而是后续实现、审查和扩展时的总设计框架。

## 设计判断

OpenCap 不能只做 MCP server 聚合，也不能只做 Registry 目录。更准确的定位是：

```text
AI Capability Control Plane + Local Runtime Kernel + Evidence Registry
```

也就是说，OpenCap 的价值不在于替某个 Agent 完成任务，而在于让任意 Host、Agent 或应用在调用真实世界能力前后，都有标准、权限、证据和可追溯行为。

## 外部标准锚点

当前设计需要同时对齐三类生态信号：

- [MCP 规范 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic)：MCP 把 base protocol、lifecycle、authorization、server features、client features 和 utilities 分层；OpenCap 应把 MCP 当作 Host-facing adapter，而不是 Runtime 核心。
- [A2A 最新规范](https://a2a-protocol.org/latest/specification/)：A2A 把 Agent Card、任务生命周期、认证授权和多传输互操作放在中心；OpenCap 未来只能映射能力发现和调用入口，不能把 Capability 伪装成 Agent。
- [OpenAI Apps SDK](https://developers.openai.com/apps-sdk)：Apps SDK 以 MCP server 和 ChatGPT app 分发为基础；OpenCap 可以成为应用背后的能力运行层，但不应绑定单一 Host 或商店入口。

结论：OpenCap 的主轴应是协议中立的 Capability Runtime，MCP 是 V1 入口，A2A、Apps SDK、OpenAPI adapter 都是互操作配置，而不是系统内核。

## 五个平面

OpenCap 的整体架构分成五个平面。每个平面有不同职责，不能互相替代。

| 平面 | 负责什么 | 不负责什么 | V1 关键产物 |
| --- | --- | --- | --- |
| 标准面 | 定义 Capability 怎么描述、打包、测试和演进 | 不判断用户是否允许执行 | Manifest schema、Capability Package、Registry tests |
| 控制面 | 管理安装、策略、确认、配额、生命周期和变更 | 不直接调用外部 API | policy、consent、quota、lifecycle、policy ledger |
| 执行面 | 把一次调用安全地变成外部请求和结构化结果 | 不做长期决策和生态排名 | Runtime pipeline、HTTP executor、Result Envelope |
| 信任面 | 保存证据、审计、来源、撤销、安全公告和质量信号 | 不覆盖本地 policy | audit log、trust card、advisory、provenance |
| 互操作面 | 把 Runtime 暴露给 MCP、CLI、未来 A2A/Apps SDK/OpenAPI | 不绕过 Runtime pipeline | MCP tools、compatibility profile、adapter records |

这五个平面是后续拆包、模块边界、测试分组和文档治理的主结构。

## 三条主链路

### 1. 能力供应链

```text
Capability author
  -> manifest.yml
  -> package lint
  -> registry tests
  -> review checklist
  -> lifecycle/trust metadata
  -> installable package
```

目标：让能力进入系统前就具备可读、可测、可审查的形态。

### 2. 调用执行链

```text
Host or CLI
  -> InvocationRequest
  -> load installed capability
  -> input validation
  -> input classification
  -> data minimization
  -> data egress gate
  -> policy decision + trace
  -> confirmation if needed
  -> quota/budget gate
  -> secret resolution
  -> executor
  -> output validation
  -> result sanitization
  -> Result Envelope
  -> audit log
  -> protocol adapter response
```

目标：任何调用，无论来自 CLI、MCP 还是未来远程 API，都必须经过同一条 Runtime pipeline。

### 3. 证据反馈链

```text
Invocation log
  -> usage event
  -> execution evidence
  -> compatibility record
  -> quality score input
  -> advisory/revocation impact analysis
  -> policy simulation input
```

目标：OpenCap 的生态质量来自证据积累，而不是中心化平台的口头认证。

## Runtime Kernel

Runtime Kernel 是 OpenCap 的核心。它只关心四个输入和一个输出：

```text
输入：
- InstalledCapability
- InvocationRequest
- RuntimePolicySet
- RuntimeEnvironment

输出：
- ResultEnvelope
```

Runtime Kernel 不应该知道 ChatGPT、Claude、Cursor、A2A 或未来 Cloud 的具体 UI。它只暴露稳定调用契约，所有 Host 差异由 adapter 和 compatibility profile 处理。公共契约的工程化展开见 `docs/设计/runtime-kernel-contract-v1.md`。

### Kernel 必须拥有的能力

- 加载已安装 Capability。
- 验证和分类输入。
- 计算最小外发数据。
- 运行 data egress gate、policy gate、quota gate。
- 构造 confirmation request 和 consent receipt。
- 在允许后解析 secret。
- 执行 HTTP capability 或 dry-run。
- 校验、净化并封装结果。
- 写入审计和证据。

### Kernel 不拥有的能力

- 不做聊天入口。
- 不做 Agent planning。
- 不做 workflow runtime。
- 不做 marketplace 排名。
- 不直接绑定某个 Host SDK。
- 不把 trust level 当作授权。

## 四种账本

OpenCap 长期要靠账本形成可治理生态。

| 账本 | 记录对象 | 用途 |
| --- | --- | --- |
| Capability Ledger | package、manifest digest、lifecycle、advisory、revocation | 知道能力从哪里来、现在是否可信 |
| Policy Ledger | policy revision、activation、rollback、override | 知道权限边界如何变化 |
| Invocation Ledger | 每次调用、输入摘要、决策、结果、错误 | 知道发生了什么 |
| Compatibility Ledger | Host、profile、版本、测试记录、失败项 | 知道在哪些 Host 上如何工作 |

V1 可以先用本地文件和 SQLite 表达这些账本，但领域对象要从第一天保持清晰。

## 四张卡片

为了让生态中的人和机器都能理解状态，OpenCap 应逐步生成四张卡片。

| 卡片 | 读者 | 内容 |
| --- | --- | --- |
| Capability Card | 用户、Host、Registry | 能力做什么、输入输出、权限、风险、安装方式 |
| Trust Card | 维护者、安全工程师 | 测试、review、maintainer、advisory、lifecycle、quality |
| Consent Card | 最终用户 | 本次调用要做什么、发给谁、风险、是否可撤销 |
| Compatibility Card | 集成者 | 哪个 Host、哪个 profile、哪些检查通过或失败 |

这四张卡片能把“生态治理”从抽象口号变成可展示、可测试、可审查的对象。

## 执行前门禁顺序

OpenCap 的安全性很大程度取决于门禁顺序。V1 必须坚持以下顺序：

1. Schema validation。
2. Input classification。
3. Data minimization。
4. Data egress policy。
5. Runtime policy decision。
6. Policy decision trace。
7. Confirmation / consent。
8. Quota / budget / abuse gate。
9. Secret resolution。
10. Execution。
11. Output validation。
12. Result sanitization。
13. Result envelope。
14. Audit write。

硬边界：egress deny、outbound private block、revoked/malicious block、audit preflight failure、secret ordering violation 不能被 override 或 breakglass 绕过。

## 互操作策略

### MCP 是 V1 协议入口

V1 只需要稳定支持 `tools/list` 和 `tools/call`。MCP tool metadata 必须由 Runtime projection 生成，不能原样透传第三方 manifest description。

### A2A 是未来 Agent 间协作入口

OpenCap Capability 不是 Agent。未来 A2A adapter 只能把一组能力包装为可发现的 Agent Skill 或受控调用入口，并且必须声明 profile、身份和授权边界。

### Apps SDK 是分发入口之一

OpenCap 可以支撑 ChatGPT App 背后的 MCP server 和能力治理，但 Apps SDK 不应成为 OpenCap 的唯一产品入口。

### OpenAPI 是导入入口

OpenAPI adapter 可以帮助生成 Capability 草稿，但不能跳过 review、least privilege、data egress、prompt-surface lint 和 registry tests。

## V1 最小生态闭环

V1 的目标不是“功能多”，而是跑通一个最小生态闭环：

```text
一个开发者写 capability package
一个 reviewer 能检查它
一个用户能安装它
一个 Host 能发现它
一次调用能被安全门禁控制
一次结果能被审计和解释
一次失败能被恢复或定位
```

只要这个闭环成立，OpenCap 就不是目录项目，也不是单个 Agent，而是 AI 原生能力生态的最小内核。

## 分阶段设计收敛

| 阶段 | 核心问题 | 成功信号 |
| --- | --- | --- |
| v0.1 Local Runtime | 能否安全执行一个 HTTP capability | validate/install/invoke/logs/serve 跑通 |
| v0.2 Evidence Registry | 能否让能力可提交、可测试、可撤销 | registry CI、trust/advisory/lifecycle 可见 |
| v0.3 Interop Profiles | 能否跨 Host 证明兼容性 | MCP Host records、conformance suite |
| v0.4 Adapter Layer | 能否接入 OpenAPI/MCP proxy/A2A draft | adapter 生成草稿但不绕过治理 |
| v0.5 Policy Operations | 能否管理组织级策略变化 | policy ledger、simulation、override runbook |
| v1.0 Capability Network | 能否让生态独立运转 | package、runtime、registry、evidence、governance 闭环稳定 |

## 设计验收问题

后续任何新增设计都要回答这些问题：

- 它属于五个平面中的哪一个？
- 它是否绕过 Runtime Kernel？
- 它产生什么证据？
- 它是否改变用户授权边界？
- 它是否把 Host 行为误当作 OpenCap 安全保证？
- 它是否需要新增 profile、ADR、任务或测试？
- 它失败时会留下什么可恢复线索？

## 当前设计缺口

- Runtime Kernel public contract 已形成设计契约，但还没有落入 `packages/runtime` TypeScript exports。
- 四种账本已落成 Runtime public storage interface；后续仍需要把具体文件/SQLite/YAML 迁移策略和生成器逐步接入实现。
- Capability Card / Trust Card / Consent Card / Compatibility Card 还没有统一生成规则。
- MCP elicitation、A2A Agent Card、OpenAPI adapter 仍是 future profile，没有 RFC。
- `pnpm build` 和 `pnpm test` 已在项目 conda 环境通过；`pnpm validate` 仍失败在 T001 范围内的 AJV draft 2020-12 meta schema 初始化问题。

这些缺口不改变 V1 入口。下一步仍然从 T001 开始，让 `opencap validate` 调用真实 schema 校验。
